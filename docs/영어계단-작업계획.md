## 1. 개발 · 배포 환경 (기준 프로젝트와 동일)

기준 프로젝트의 설정을 그대로 이식한다. 달라지는 부분만 아래에 명시한다.

| 항목 | 기준 프로젝트 | 영어계단 |
|---|---|---|
| 언어·빌드 | TypeScript strict + Vite 7 | 동일 |
| 배포 | Cloudflare **Workers Static Assets** (`wrangler.jsonc`, `main` = `src/worker/index.ts`, `assets.directory=./dist`) | 동일. `name: "infinite-english"` |
| 404 처리 | `not_found_handling: "404-page"` (멀티페이지이므로 SPA 모드 금지) | 동일 — `index.html` + `quality.html` 멀티페이지 |
| 랭킹 DB | D1, 단 `d1_databases`는 **주석 처리**로 시작 (없는 database_id로 배포하면 조용히 깨짐) | 동일 패턴. MVP는 로컬 저장만, 기록 공유는 Phase 8 |
| PWA | `vite-plugin-pwa` (autoUpdate, 오프라인 플레이) | 동일. 단 **glb 는 프리캐시에서 제외**하고 `/models/*.glb` 를 CacheFirst 런타임 캐시로 둔다 (4.2절) |
| 캐시 정책 | `public/_headers` — `/assets/*` immutable, html no-cache | 동일 + `/models/*` immutable (파일명에 해시 부여) |
| dev 서버 | `host: true`, 5173 (실기기 확인용) | 동일 |
| npm scripts | `dev` `build`(tsc --noEmit && vite build) `preview` `typecheck` `deploy` `sim` | 동일 + **`assets`**(3D 에셋 최적화) |
| 문서 | `docs/*.md` + README에 링크 | 동일 |

**추가 의존성**

```
three                          # 렌더러 (설치본 0.185)
@gltf-transform/core           # (dev) 에셋 파이프라인 — 병합·프루닝·머티리얼 dedupe
@gltf-transform/functions      #        mergeDocuments / dedup / prune
@gltf-transform/extensions     #        KHR_texture_transform 등 원본 확장 보존
vitest                         # (dev) 학습 엔진 로직 회귀 테스트 ※ 기준 프로젝트에는 없으나 추가 권장
```

> `typescript` `vite` 는 기준 프로젝트와 같은 메이저에 맞춘다(5.9 / 7.x). 최신 설치본은
> TypeScript 7 · Vite 8 로 올라가지만, "환경 동일"이 이 프로젝트의 전제이므로 고정한다.

> 기준 프로젝트는 테스트 스크립트가 없다. 여기서는 Mastery·Spaced Repetition·Adaptive 난이도가
> **눈으로 검증 불가능한 로직**(며칠 뒤의 재출제 시점 등)이라 단위 테스트 없이는 회귀를 못 잡는다.
> 렌더링·연출은 테스트하지 않고 로직 3개 모듈만 대상으로 한다.

**React를 쓰지 않는다** — 기준 프로젝트와 같은 이유. 60fps three.js 루프가 렌더의 주체이고,
퀴즈 패널·오버레이는 상태 전이 시점에만 갱신되는 정적 구조다.

## 2. 3D 스택 선정

| 후보 | 판단 |
|---|---|
| **three.js** ✅ | glTF 로더·SkinnedMesh·AnimationMixer·InstancedMesh가 표준 탑재. Kenney/KayKit 에셋이 전부 glTF이므로 변환 없이 그대로 쓴다. gzip 후 약 160KB |
| Babylon.js | 기능은 충분하지만 번들이 2~3배. 물리·에디터 등 이 게임에 필요 없는 기능 비중이 큼 |
| 순수 WebGL | 스키닝 애니메이션을 직접 구현해야 함. 캐릭터 애니 32종을 손으로 다룰 이유가 없다 |
| React Three Fiber | React를 끌어들이는 비용 대비 이득 없음 (1장 참고) |

**렌더 방침** — 저사양 태블릿 30fps 이상이 하한선이다.

- 포스트프로세싱 **미사용** (모바일 fill-rate 즉사 요인)
- 조명 = `HemisphereLight` + `DirectionalLight` 1개. 실시간 그림자는 **blob 그림자 데칼**로 대체하고,
  `shadowMap`은 고사양 옵션에서만 512px 단일 캐스터로 켠다
- 계단·프롭은 `InstancedMesh`. 스키닝은 플레이어 1체 + 펫 1체 + 보스 1체까지만
- DPR 상한 2 (저사양 모드 1.25), `antialias`는 DPR 1.5 미만에서만 on
- 카메라는 **원근 투영 고정각** (수직 회전 없음) — 계단 지그재그의 좌/우 판단이 항상 같은 화면 방향이어야 한다

**성능 예산 (한 프레임)**

| 지표 | 목표 |
|---|---|
| draw call | 60 이하 |
| 삼각형 | 150k 이하 |
| 스키닝 캐릭터 | 3체 이하 |
| 초기 다운로드(모델) | **3MB 이하** (월드 추가분은 lazy, 월드당 1MB 이하) |
| fps | 폰·아이패드 60 / 보급형 안드로이드 태블릿 30 |

## 3. 게임 설계 — 3D 무한 계단

### 3.1 핵심 조작 (원작형 방향 판단 채택)

문제 풀이(사고)와 방향 탭(반사)을 **시간적으로 분리**한다. 둘을 동시에 요구하면 인지 부하가 겹쳐
어느 쪽도 제대로 안 된다.

```
문제 출제 → 보기 4개 중 선택
   ↓ 정답
계단 구간 N칸 생성 (콤보에 따라 N 증가)
   ↓
좌/우 탭으로 N칸을 연달아 오른다  ← 원작 무한의 계단 구간
   ↓
구간 통과 → EXP/GOLD → 다음 문제
```

**콤보가 곧 계단 길이다.** 정답 보상이 숫자가 아니라 게임 액션으로 나타난다 (PRD 35장 3항).

| 콤보 | 구간 길이 | 계단 연출 |
|---|---|---|
| x1~2 | 1칸 | 일반 |
| x3~4 | 2칸 | 일반 |
| x5~9 | 3칸 | GOLD STEP |
| x10~19 | 4칸 | FIRE STEP |
| x20+ | 4칸 + 시간 보너스 | LIGHTNING STEP |

### 3.2 방향 실수 페널티 (설계 핵심) — **2026-08-12 뒤집었다**

원래 설계(아래 표의 "당초")는 조작 실수로 판이 끝나지 않게 했다. **요청으로 뒤집었다** —
계단의 긴장이 방향 선택에서 오고, 실수해도 죽지 않으면 계단이 그냥 통과 구간이 된다.

| 사건 | 당초 설계 | **현재** |
|---|---|---|
| 영어 오답 | HP -1, 콤보 리셋, 오답 큐 등록 | 그대로 |
| 방향 실수 | 휘청(0.4초) + 콤보 하락. HP 불변 | **즉시 판 종료** (HP·REVIVE 를 거치지 않는다) |
| 같은 구간 3회 실수 | 구간 자동 통과 | **없음** — 첫 실수에서 끝난다 |
| 계단 한 칸 체류 시간 초과 | (없었음) | **즉시 판 종료** — 계단 타이머 (3.2.1) |
| 구간 제한시간 초과(Escape 이벤트) | 콤보 리셋만 | 그대로 (HP 불변) |

> **당초 근거는 여전히 유효하다**: "HP를 방향 실수와 공유하면 영어를 틀려서 실패했다는 인과가
> 흐려진다." 그래서 HP 는 건드리지 않고 **별도 종료 경로**(`Session.fail`)로 끝낸다 —
> 방향 실수가 HP 를 깎지는 않는다. 인과 문제는 남으므로 완화 장치를 둔다:
>
> · `방향 자동 보정`(`?autodir=1`) — 켜면 어느 쪽을 눌러도 맞는 방향이 되어 **방향으로 죽지 않는다.**
>   저학년·소근육 발달 차이를 조작 난이도로 걸러내면 안 된다는 원칙은 그대로다
> · 결과 화면이 **종료 사유를 구분**한다 — "방향을 틀렸어!" / "시간이 다 됐어!" / "아깝다!"
>   그리고 사유별로 다음에 할 일을 알려 준다. "아깝다!"만 보여 주면 무엇을 고쳐야 할지 모른다

#### 3.2.1 계단 타이머

한 칸에 머무를 수 있는 시간. 한 칸을 밟을 때마다 다시 찬다. 0 이 되면 판이 끝난다.

| | |
|---|---|
| 0층 | 5.0초 |
| 층당 감소 | 0.01초 |
| 하한 | **2.0초** — 300층에서 도달. 없으면 어느 층부터 인간이 반응할 수 없다 |
| 보스전 | **적용 안 함** — 계단이 잠긴 구간이고, 문제를 읽을 시간을 빼앗으면 안 된다 |
| 문제 푸는 중 | 멈춘다 |
| 시작 시점 | **정답 피드백이 끝난 뒤** — 연출 0.25초가 아이 시간에서 깎이면 2초 층에서는 12% 다 |

게이지는 보스 HP 바와 같은 자리에 그린다(둘은 동시에 뜨지 않는다). 남은 30% 부터 붉게
깜빡이고, `prefers-reduced-motion` 이면 색만 바뀐다.

구현 주의: 방향 실수로 죽는 연출(0.55초) 중에는 타이머를 멈춘다. 안 멈추면 종료 사유가
'timeout' 으로 덮여 **아이가 잘못된 이유를 본다.**

### 3.3 계단 생성

- 계단 i+1 = 계단 i + `(±X, +Y)` — 좌/우 지그재그, 높이 일정
- 방향 시드는 `core/rng.ts`(시드 난수)로 결정 → 리플레이·시뮬레이터 재현 가능
- 화면 밖(아래) 계단은 **풀로 회수**해 위쪽에 재배치. 상시 유지 계단 수 ~24칸
- 10·20·30·50층 체크포인트에서 계단 재질·프롭 세트 교체 → "올라왔다"는 감각을 시각으로 준다
- 카메라는 Y를 스프링 추적, X는 캐릭터 X를 감쇠 추적 (지그재그가 화면을 흔들지 않게)

### 4.1 에셋 파이프라인 (구현 완료 — Phase 0)

원본 kit 폴더(총 168MB)를 `public/`에 넣지 않는다. 화이트리스트에 적힌 모델만 bundle 단위로
병합해 `public/models/`로 낸다.

```
npm run assets     # tools/optimize-assets.mjs + tools/asset-manifest.json
```

1. 화이트리스트(`asset-manifest.json`)의 glb만 수집 — 없는 이름은 에러로 막는다
2. bundle 단위 **하나의 glb로 병합**. 각 모델은 `<모델명>` 래퍼 노드로 감싸 이름으로 꺼낸다
3. `mergeDocuments` → 버퍼 통합 → `dedup()` → `prune({ keepLeaves: true })`
4. 산출: `public/models/*.glb` + `manifest.json`(bundle·노드 목록·용량). 산출물은 커밋한다

> **병합의 실제 이득은 바이트가 아니라 요청 수와 머티리얼 공유다.** Kenney glb는 아틀라스를
> 내장하지 않고 `Textures/colormap.png`를 **외부 URI로 참조**한다(kit당 7~12KB 1장). 따라서
> 개별 로드해도 텍스처는 브라우저가 한 번만 받는다. 병합으로 얻는 것은 ① 45요청 → 6요청,
> ② `dedup()`이 머티리얼을 하나로 합쳐 셰이더 프로그램·draw call이 줄어드는 것이다
> (food 25모델 → 머티리얼 1종, 실측).

**`prune()`의 기본값을 쓰면 안 된다** — 본(bone)은 메시가 없는 리프 노드다. 기본
`keepLeaves: false`로 돌리면 애니메이션 타겟인 본이 지워지고, 클립은 경고만 남기며 조용히
아무것도 움직이지 않는다.

#### 스킨드 캐릭터는 bundle 하나에 하나만 (파이프라인이 에러로 막는다)

같은 리그를 쓰는 캐릭터 2개를 한 glb에 합치면 본 이름(`hips`, `hand.r` …)이 중복되고,
three의 GLTFLoader가 뒤에 오는 쪽에 `_1`을 붙여 유일화한다. 그러면 공유 클립의 트랙 이름과
본 이름이 어긋나 **경고만 남기고 애니메이션이 멈춘다.** 프롭(스킨 없음)은 이름이 겹쳐도
애니메이션에 영향이 없으므로 얼마든 병합해도 된다.

같은 이유로 **애니메이션 전용 bundle은 리그를 통합한다** — 애니메이션 파일 2개를 병합하면
리그가 2벌 들어오므로, 첫 리그를 정본으로 두고 모든 채널을 이름으로 재바인딩한 뒤 중복을 지운다
(`mergeRigs()`, 채널 754개 재바인딩 실측).

#### three의 노드 이름 정규화

three는 노드 이름에서 `.` `:` `/` `[` `]`를 제거한다(`PropertyBinding.sanitizeNodeName`).
원본의 `hand.r`은 씬에서 `handr`이 된다 — **원본 이름으로 `getObjectByName`하면 못 찾는다.**
런타임 코드는 조회 시 반드시 같은 정규화를 적용할 것.

### 공정

| 단계 | 내용 | 산출 |
|---|---|---|
| 1. 시드 | 교육부 「초·중학교 영어과 교육과정」 별표 기본어휘 + 초등 교과서 공통 어휘를 CSV로 정리 | `tools/seed/words.csv` (word, 학년, 품사) |

### 자동 검증 규칙 (`tools/build-words.ts`)

| 검사 | 실패 예 |
|---|---|
| **뜻 충돌** — 같은 레벨대에 뜻이 동일/유사한 단어 쌍 | `ancient`(고대의)와 `old`(옛날의)가 서로의 오답이 되면 정답을 골라도 오답 처리된다 |
| 예문에 표제어 포함 | `ancient` 예문에 ancient가 없음 |
| 예문 난이도 | 예문에 표제어보다 높은 레벨 단어가 2개 이상 |
| 예문 길이 | 초등 8단어 / 중등 12단어 초과 |
| 품사 일치 | 품사가 adjective인데 뜻이 "고대"(명사형) |
| 한국어 뜻 형식 | 형용사는 "~한/~의", 동사는 "~다"로 끝나는지 |
| 금칙 | 폭력·성·질병 등 아동 부적절 어휘 |
| `clozeIndex` 유효성 | 빈칸 위치가 표제어 토큰을 가리키는지 |

> **가장 중요한 검사는 뜻 충돌이다.** 기준 프로젝트에서도 같은 계열의 버그(오답이 정답과 같은 값)로
> 전수 검사 400개 중 200개가 걸린 전례가 있다. 생성기 여러 곳에 흩어 막으면 반드시 하나를 빠뜨리므로,
> **빌드 시점 한 곳에서** 걸러 `meaningAlt`로 기록하고 런타임 오답 후보에서 제외한다.

**음성(TTS)**: MVP는 Web Speech API(무료). 지원이 불균등하므로 없으면 조용히 생략한다.
V2에서 사전 생성 오디오로 교체 (단어 1,000개 × 20KB ≈ 20MB → lazy·레벨별 분할 필수).

## 8. 학습 엔진 사양

### 8.1 출제 비율 (PRD 8장)

신규 50 / 복습 30 / 취약 15 / 보너스 5. **파도형 난이도 곡선**(PRD 24장)을 20문항 템플릿으로 고정하고,
개인 `theta`를 오프셋으로 얹는다. 같은 단어 연속 출제 금지(직전 3문항 제외 창).

### 8.2 Adaptive (IRT 1PL 간이)

```
p(정답) = 1 / (1 + exp(-(theta - difficulty)))
정답: theta += K * (1 - p)     오답: theta -= K * p
K = 0.35 (calibration 중) → 0.12 (이후)
|Δtheta| ≤ 0.15 / 문항   ← 급변 금지 (PRD 7장)
```

출제는 **목표 정답률 75~80% 밴드**에서 고른다. 너무 쉬우면 지루하고 60% 미만이면 이탈한다.
Calibration은 쉬움-보통-어려움을 섞은 10문항으로 초기 `theta`·`confidence` 추정.

### 8.3 Spaced Repetition

세션 내 큐와 세션 간 큐를 **분리**한다 (하나로 합치면 30초 후 재출제와 3일 후 재출제가 같은 자료구조에서 싸운다).

| 큐 | 간격 |
|---|---|
| 세션 내 (초) | 오답 → 30초 → 5분 |
| 세션 간 (일) | 다음 게임 → 1일 → 3일 → 7일 → 21일 (SM-2 ease factor 조정) |

### 8.4 Mastery (PRD 9장)

5단계. 100% 도달 조건은 정답 횟수가 아니라 **유형 게이트**다.

```
EN→KO 정답 ✓   KO→EN 정답 ✓   문맥/문장 정답 ✓   24시간 이후 재출제 정답 ✓
→ WORD MASTER
```

#### 검증기가 잡아낸 실제 오류 (기록)

파이프라인의 값은 여기서 드러난다. 1차 배치에서 사람이 놓친 것을 빌드·테스트가 잡았다.

| 유형 | 사례 | 결과 |
|---|---|---|
| **동음이의 — 정답이 두 개** | `eye`(눈)와 `snow`(눈), `sun`(해)와 `year`(해), `moon`(달)과 `month`(달) | 뜻 표기를 `눈(신체)`/`눈(날씨)` 로 구분. KO→EN 문제에서 정답이 둘이 되는 것을 막았다 |
| 동의어 미선언 | `small→little`, `happy→glad`, `difficult→hard` 가 DB 에 없는 단어를 가리켰다 | 단어를 추가하고 **양방향 선언**을 강제 |
| 동의어 단방향 선언 | `watch` 는 `look` 을 적었지만 `look` 은 비어 있었다 | 빌드 실패 → 수정 |
| **보기 중복** | `big` 의 오답에 `small`(작은)과 `little`(작은)이 함께 들어가 보기가 "작은/작은" | 빌드에서 뜻 기준 후보 중복 제거 + 런타임에서 렌더 문자열 기준 이중 방어 |
| 예문이 표제어보다 어려움 | `strong` 예문에 DB 밖 단어 3개(man/lifts/box) | 아는 단어로만 다시 씀 |
| **정답이 두 개** (L5 배치) | `happen`(일어나다)과 `get up`(일어나다) | happen 을 "발생하다"로 |
| 표제어 중복 (L3 배치) | `bread` 를 L1 과 L3 에 각각 넣었다 | L3 행 삭제 |
| **검증 규칙의 오탐** | `ocean`(바다)이 "명사인데 '다'로 끝난다"에 걸렸다 | 형태소 분석기 없이는 못 가르는 경우 — 예외 목록(`NOUN_ENDING_IN_DA`)으로 두고 주석에 한계를 남겼다 |
| 오답 후보가 없는 범주 | `energy` 의 `science` 태그에 단어가 1개뿐 | 관련 단어에 태그를 겹쳐 붙여 5개로 |

> **정답 위치 분포 테스트가 처음에 실패했는데, 원인은 게임이 아니라 테스트였다.** 문제마다
> 시드를 새로 만들어(`단어 길이 × 977 + …`) 시드가 서로 비슷해지자 같은 순열이 반복됐다
> (15.4% / 31.2%). 게임처럼 **하나의 난수 스트림**에서 연달아 뽑도록 고쳐야 셔플 자체를 검사한다.

|---|---|
| 발견 경로 | 단어를 추가한 뒤 "런타임이 새 레벨을 읽는가"를 확인하다 `LEVELS = [1,2,3,4,5]` 를 발견. 가정하지 않고 풀 해결 개수를 실측해 2개(village 1개, museum 1개)를 특정했다 |

> **난이도 목표가 약간 높게 잡혀 있다**는 뜻이다 — Phase 9 에서 조정한다.

**가상 학생 시뮬레이션 (100문항, 실력별)**

| 실제 실력 | 관측 정답률 | theta 수렴 | 신규/복습/취약/보너스 |
|---|---|---|---|
| 2 (초3 시작) | 64% | 1.90 | 40/44/12/4 |
| 3.5 | 70% | 3.27 | 39/46/12/3 |
| 5 | 71% | 4.63 | 39/45/12/4 |
| 6.5 | 84% | 6.78 | 46/37/13/4 |

theta 는 네 경우 모두 실제 실력으로 수렴한다. 다만 **정답률이 목표 밴드(75~85%)보다 낮다** —
64~71%. 원인은 둘이고, 둘 다 의도된 설계의 결과다.
 1. 세션에 **틀린 단어 재출제가 강제로 섞인다**(PRD 35장 5항). 목표 밴드는 신규 문항 선택의
    기준이고, 재출제를 포함한 판 전체 정답률은 그보다 낮게 나온다.
 2. 실력이 콘텐츠 하한(Level 1)에 붙어 있으면 아무리 쉬운 단어를 내도 정답 확률에 상한이 생긴다.
Phase 9 밸런싱에서 **목표 정답률 상수(`TARGET_ACCURACY`)와 복습 비율**을 실제 학생 데이터로
조정할 항목으로 남긴다. 지금 시뮬레이션 학생에 맞춰 상수를 돌리는 것은 의미가 없다.

#### 단위 테스트가 잡은 버그 (기록)

세 개 모두 **화면으로는 발견할 수 없는** 종류였다.

| 버그 | 증상 | 원인 |
|---|---|---|
| **적응 난이도 부호 오류** | 목표 난이도가 실력보다 **위**로 잡혔다 (정답률 기대치 20%) | `d = theta + ln(p/(1-p))` 를 써야 할 곳에 부호를 뒤집어 씀 |
| SR 첫 간격이 1일 | 첫 판에서 복습 후보가 전부 미래 시점이 되어 **복습 30% 를 채울 수 없었다** | 정답 간격 단계를 `[0일, 1일, …]` 로 시작 → `[3분, 1일, …]` 로 수정 |
| 난이도 보정 단위 혼용 | 파도 보정 0.14 가 unit 축이라 **1.26레벨 점프**가 됐다. 하한 실력 학생의 정답 확률이 70%→27% | 난이도 계산을 전부 레벨 축으로 통일 (`targetLevelRange`) |

여기에 데이터 쪽 문제 하나가 더 있었다. `build-words.ts` 가 난이도에 **하한 0.05** 를 걸어
가장 쉬운 단어가 레벨 1.45 였다 — 이제 시작하는 초3 학생의 정답률 상한이 63% 로 묶였다.
Level 1 고빈도 단어(cat·dog·apple)는 커리큘럼의 바닥이므로 난이도 0 이 맞다. 하한을 없앴다.

#### 실측이 잡은 밸런스 문제

**콤보가 최고조인 플레이어는 한 문제에 4칸을 오른다 — 20층이면 5문제다.** 층 조건만 두면
5~6문제마다 보스를 만나고 보스전이 8~10문제이므로 **판 전체가 보스전**이 되어 버렸다.
계단을 오르는 리듬이 이 게임의 주인공이므로, 보스에 **문제 수 간격(10문제)** 을 추가했다.

> 이 문제는 "이벤트가 하나도 안 뜬다"는 증상으로 처음 나타났다. 원인을 추적하니 이벤트 로직은
> 정상이었고(보스전 중에는 이벤트를 내지 않는 것이 설계다), **판이 거의 보스전이라** 이벤트를
> 굴릴 기회 자체가 없었던 것이었다. 계측(`__ie.eventDebug`)을 넣어 "주기 통과 횟수"와
> "발생 횟수"를 분리해 보고서야 알았다 — 추측으로는 세 번 헛짚었다.

또 하나: **fps 가 120 → 30 으로 떨어져 보였는데 게임이 아니라 환경이었다.** 순수
`requestAnimationFrame` 속도를 재니 30Hz 였고, 프레임 간격 중앙값 33.3ms · 끊긴 프레임 0/59 로
게임은 주어진 프레임을 모두 소화하고 있었다. **fps 만 보고 회귀라고 판단하면 안 된다** —
rAF 속도와 프레임 간격 분포를 같이 봐야 한다.

#### 시뮬레이션으로 수치를 골랐다 (200문항 × 40회, 정답률 78%)

"보스를 늘리면 계단 오르기가 살아나는가"를 추측으로 정하지 않고 실제 상수로 계산했다.

| 설정 | 도달 층 | 계단 구간 문제 | 보스전 문제 | 보스전 평균 길이 |
|---|---|---|---|---|
| 변경 전 (20층 · 1~4칸) | 154층 | **45%** | 55% | 15.0문제 |
| 보스 10층 · 구간 4~12 · HP 상한 320 | 124층 | 8% | 92% | 19.9문제 |
| **채택: 보스 10층 · 구간 4~12 · HP 상한 240** | **140층** | **8%** | 92% | **17.9문제** |
| 보스 15층 · 구간 4~12 · HP 상한 320 | 153층 | 11% | 89% | 18.6문제 |
| 구간 유지(1~4) · 보스 10층 | 90층 | 24% | 76% | 17.7문제 |

- **HP 상한을 320 → 240 으로 내린 근거가 여기 있다.** 도달 층은 124 → 140 으로 올라가고
  보스전은 19.9 → 17.9문제로 짧아졌다 — 두 축이 함께 좋아진다. 그러면서도 100층 보스의
  체력은 변경 전(200)보다 높다
- 계단 구간에서 나오는 문제 비율이 **45% → 8%** 다. 요청의 핵심("몇 칸 오를 때마다 문제가
  나온다")은 이 수치가 답한다

#### 남은 위험 — 정직하게 적는다

| | |
|---|---|
| **보스전이 길다** | 평균 17.9문제(약 2분)다. 계단을 오르는 시간은 판 전체의 5% 뿐이다. 애초에 한 문제(≈6초)가 계단 13칸(≈0.45초/칸)에 해당하므로 **변경 전에도 5% 였다** — 나빠진 것이 아니라 원래 그랬다. 더 줄이려면 `BOSS_EVERY` 를 15로 올린다(계단 구간 문제 11%, 도달 153층) |

|---|---|---|

#### 2번 — 좌표 버그의 정체

`OFFSET = (0, +0.1, −2.2)` 를 플레이어 위치에 더했다. 계단은 한 칸당 `y +0.46 · z −0.78` 로
**올라가면서 안쪽으로** 뻗는다. z 만 2.2 밀고 y 를 0.1 만 올리면 그 깊이의 계단 표면(약 +1.3y)
보다 **1.2유닛 아래**다 — 보스가 계단에 박히거나 허공에 뜬 것처럼 보였다.

이제 좌표는 `Stairs` 만 만든다. `BossActor` 는 받은 표면 좌표에 서고, 스스로 계산하지 않는다.
테스트가 옛 방식이 틀렸다는 것과 새 방식이 맞다는 것을 함께 고정한다.

##### 배치 버그를 테스트가 잡았다

원경 블록을 근경 루프 안에 뒀더니 `i % 3` 을 이미 통과한 층만 검사해 **3과 7의 공배수
(21칸)마다만** 놓였다 — 한 화면에 1~2개. 별도 루프로 분리했다.

그리고 처음 쓴 검증 두 개가 **내 쪽이 틀렸다**:

1. "원경은 현재 층 표면보다 낮다" → 계단이 올라가므로 앞쪽 원경은 현재 층보다 높은 것이
   정상이다. 기준은 현재 층이 아니라 **그 오브젝트가 놓인 층**이다
2. "`|x| > 6.6` 이면 원경" → 프롭 x 는 `계단 x + 이격거리` 이고 계단 x 는 지그재그로
   표류하므로 근경도 6.68 까지 나온다. **크기로 갈라야 한다**(근경 ≤1.35 / 원경 ≥1.7)

#### Playwright 검증 (2026-08-12) — **테스트가 통과했는데도 4개가 깨져 있었다**

단위 테스트 128개와 타입체크를 모두 통과한 상태에서 브라우저를 열었다. 네 가지가 나왔다.
전부 **"배치했다 ≠ 동작한다/보인다"** 유형이다.

| # | 증상 | 원인 | 조치 |
|---|---|---|---|
| 1 | 10층 보스를 만나고도 **27층까지 올라갔다** | `session.boss` 는 `startBossFight` 에서, `phase` 는 그 뒤 0.9초(등장 연출) 후에야 바뀐다. 그 사이 `phase === 'climbing'` 이라 입력이 통과했다 — **관문이 성립하지 않았다** | 등장을 **예약하는 순간** 잠그는 `bossPending` + `canClimb()` 도입. 입력·힌트·프롬프트·스프링 자동입력이 모두 이 하나를 본다 |
| 2 | 보스 옆에 **흰 사각형**이 떠 있다 | 배경 구름이 `BoxGeometry` + 흰 무광 재질이라 하드 엣지 판으로 보였고, 피치 범위(5.5~17.5°)가 화면 중앙까지 내려와 계단·보스와 자리를 다퉜다 | 20면체를 납작하게(저폴리 화풍) + 피치를 **4~9°** 로 좁혀 화면 맨 위 띠로 올렸다 |
| 3 | 보스전 중 하단에 **"오른쪽 ▶ · 다음 보스 20층"** | update 루프가 `phase === 'climbing'` 만 보고 보스 안내를 등반 안내로 덮어썼다 | 프롬프트 갱신도 `canClimb()` 로 통일. 보스전에는 "보스를 넘어야 한다!" |
| 4 | **프롭이 화면에 한 개도 없었다** | 세로 화면 프러스텀이 좁다. fov 42°·비 0.49 → 수평 반각 10.6°. 22칸 앞의 화면 반폭이 5.0 인데 프롭을 3.4~6.6, 원경을 9~15.5 에 뒀다 — 전부 프레임 밖. 화면의 초록 원뿔은 프롭이 아니라 **배경 실루엣**이었다 | 근경 **2.6~4.8**, 원경 **5.0~8.0**(낙차 3~7). 프러스텀 안 인스턴스를 세는 `propVisibility()` 훅으로 0개 → 근경 6~11 · 원경 4개 확인 |

> **1번과 3번은 같은 뿌리다.** "계단을 오를 수 있는가" 를 여러 곳에서 각자 판단하고 있었다.
> `canClimb()` 하나로 모으자 둘이 함께 사라졌다.
>
> **4번은 단위 테스트가 잡을 수 없었다.** `placement.test.ts` 는 "배치되는가" 를 검증했고
> 그건 통과했다 — 문제는 "보이는가" 였고 그건 카메라를 알아야 한다.

##### `__ie.tap` 이 거짓 검증을 만들었다

첫 시도에서 잠금을 넣었는데도 여전히 27층까지 올라갔다. 원인은 **훅이 게이트를 우회**한 것이었다 —

#### 타이밍을 setTimeout 으로 맞추지 않았다

두 가지 이유가 있고, 둘 다 이 프로젝트에서 이미 겪은 것이다.

1. **연출 지연이 단일 슬롯을 공유한다.** `after()` 는 `clearTimeout` 후 하나만 예약한다 —
   피격을 `after(0.24, ...)` 로 잡으면 오답 피드백 타이머(`after(1.1, ...)`)와 서로를 취소한다.
   보스 등장이 스프링 기믹에게 취소당한 일이 실제로 있었다
2. **시간은 프레임과 어긋난다.** 프레임이 밀리면 타격이 닿는 순간과 아파하는 순간이 벌어진다

그래서 `BossActor.takeImpact()` 가 **돌진 진행도 40%(정점)를 지나는 프레임에 한 번만** 신호를
주고, update 루프가 받아서 피격을 시작한다. 신호는 **소비형**이다 — 불리언을 켜 두면
매 프레임 리액션이 다시 시작된다.

- 블록: 여러 종류를 섞는지 · 한 종류가 80% 를 넘지 않는지 · **배율 0.5 로 정규화되는지** ·
  보이는 구간만 그리는지(5,000층에서도 인스턴스 수 일정)

### 상점 실기능 — 무기·캐릭터 구매·장착 (2026-08-13 요청) — **완료**

"UI 만 추가하고 추가 예정" 이었던 상점을 **실제로 사고 쓰는 기능**으로 바꿨다.
아이템은 요청받은 가격을 그대로 넣었다 (무기 22종 1,000~5,000 · 캐릭터 6종 5,000~10,000).

#### 가격을 정하기 전에 재화를 시뮬레이션했다

게임의 실제 골드 함수(`goldForAnswer`·`goldForCheckpoint`·`bossReward`·`instantGold`·미션 표)를
import 해서 하루 5판을 돌렸다. 수치를 베끼면 밸런스를 고칠 때 시뮬레이션이 조용히 거짓이 된다.

| 실력(정답률) | 평균 도달 층 | 5판 골드 | +미션 | 하루 총합 | 100층 도달률 |
|---|---|---|---|---|---|
| 처음 (62%) | 15층 | 581 | 139 | 720 | 0% |
| 보통 (72%) | 23층 | 1,300 | 139 | 1,439 | 0% |
| 익숙 (85%) | 49층 | 4,468 | 139 | 4,607 | 10% |
| 아주 잘함 (93%) | 75층 | 8,393 | 139 | 8,532 | 50% |

100층 완주 1판은 **2,465골드**이고 그중 **61% 가 보스 처치**다(체크포인트 15% · 크리스탈 13% ·
정답 7% · Treasure 3%). 일일 미션 139골드는 **하루 1회**다(판마다가 아니다).

##### 시뮬레이션이 드러낸 밸런스 문제 (미해결)

**보통 실력은 100층에 도달할 수 없다** — 도달률 0%, 종료 사유의 절반이 영어 오답이다.
100층 완주에 문제 63개가 필요한데 **HP 3 + REVIVE 1회 = 오답 4번**이 한계이고 회복 수단이 없다.
즉 정답률이 사실상 94% 이상이어야 한다. 해결 방향(체크포인트 HP 회복 · 보스 처치 시 회복 ·
HP 상향)을 보고했고 아직 선택을 받지 못했다.

#### 리그가 두 개가 되면서 클립 이름을 추상화해야 했다

상점 캐릭터(KayKit Adventurers)를 넣기 전에 리그를 열어 확인한 결과:

| | 기본 캐릭터 (Kenney) | 상점 캐릭터 (KayKit Adventurers) |
|---|---|---|
| 애니메이션 | glb 에 32종 내장 | **0개** — 보스와 같은 `Rig_Medium` 이라 `boss-anims` 26종을 빌린다 |
| 대기·점프·피격 | `idle` · `jump` · `fall` | `Idle_A` · `Jump_Full_Short` · `Hit_A` |
| 손 본 | **없다** (본 7개: root·다리2·torso·팔2·head) | `handslot.r` — 무기 슬롯이 있다 |

`Climb` 이 클립 이름을 직접 부르고 있었다. 그대로 캐릭터를 바꾸면 **애니메이션이 전부 죽는다.**
그래서 `Actor` 에 **역할 사전**을 넣고(`ClipRole`: idle·jump·hurt·no·attack·cheer)
게임 코드는 `playRole('hurt')` 로 부른다. 리그에 없는 역할은 조용히 넘긴다 —
던지면 캐릭터를 바꿨을 때 게임이 멈춘다.

무기 부착도 리그별로 다르다. 기본 캐릭터는 손이 없어 **팔 끝**에 붙인다(Kenney 공식 샘플도
그렇게 한다). "제대로 쥔 모습"을 보려면 상점 캐릭터를 사야 한다 — 제약이지 버그가 아니다.
그리고 three 는 `hand.r` 을 `handr` 로 바꾸므로(스파이크 A 에서 애니메이션이 죽은 원인)
후보 이름을 **정규화해서** 찾는다.

#### 설계 판단

- **구매 함수가 상태를 바꾸지 않는다.** `buy()` 는 결과만 돌려주고 저장·화면 갱신은 부르는
  쪽의 일이다 — 그래야 저장소 없이 테스트할 수 있다
- **산 캐릭터를 레벨 해금 캐릭터와 한 목록에 섞는다.** 아이에게는 둘 다 "내 캐릭터"이고
  잠금 규칙만 다르다(레벨이냐 골드냐). `unlockLevel: 0` + ⭐ 표시로 구분한다
- **화살은 항목이 아니다.** 활에 종속시켜 활을 들면 함께 붙는다 — 화살만 사는 것은
  게임에서 의미가 없다. 방패도 제외했다(공격 모션에 쓸 수 없다)
- **무기·캐릭터 번들은 lazy.** 산 직후에 받아 두고, 못 받아도 목록에는 남는다 —
  다음 로드에서 다시 시도한다. 무기 때문에 게임이 멈추면 안 된다
- 저장 스키마 **버전을 올리지 않았다**(`levelBand` 와 같은 이유)

#### 테스트 200항목 (+16)

`shop.test.ts` 23항목으로 다시 썼다. 화면에서 "사기" 를 누르는 것은 눈으로 알지만,
**골드가 정확히 깎이는지 · 두 번 사지 못하는지 · 산 캐릭터가 로비 목록에 실제로 들어오는지**는
눈으로 확인하기 어렵다:

- 요청받은 가격 28개가 **그대로 들어갔는지** + 표에 없는 항목이 몰래 없는지
- 가격 오름차순 · id 중복 · 화살 종속 · 방패 제외 · 활은 시위 있는 모델
- 구매: 정확한 차감 · 딱 맞는 골드 · 부족 · **중복 구매 거절**(골드만 사라지는 최악의 버그) ·
  없는 id 거절 · **인자를 변형하지 않음**
- 산 캐릭터가 `availableCharacters` 에 들어오는지 · **`rig: 'rigMedium'` 으로 표시되는지**
  (틀리면 캐릭터가 T 포즈로 선다)

`climb.test.ts` 는 스텁을 버리고 **실제 `Actor`** 를 쓴다 — 역할 사전이 검증되지 않으면
상점 캐릭터에서 조용히 깨진다. Rig_Medium 리그로 `Hit_A`·`Throw`·`Death_A` 가 나오는지 고정했다.

#### 미확인

Playwright 를 돌리지 않았다. **무기가 손(팔)에 붙은 모습·공격 동작·상점 캐릭터의 크기와
자세는 육안 확인이 필요하다.** 특히 기본 캐릭터의 팔 부착 보정값(`FIT.kenney`)은
계산으로 넣은 값이라 눈으로 봐야 한다.

#### Playwright 검증 (2026-08-13) — 부팅이 깨지는 버그와 무기 정렬 문제를 잡았다

테스트 200항목과 타입체크를 모두 통과한 상태에서 브라우저를 열었다.

##### 1. 상점 캐릭터로 저장하면 **다음 접속에 부팅이 깨졌다**

```
Error: bundle 'boss-anims' 을 먼저 load() 해야 한다
  at buildActor (main.ts:109) at boot (main.ts:131)
```

상점 캐릭터는 클립이 0개라 `boss-anims` 를 빌려 쓴다. 그런데 그 번들은 **lazy** 이고
부팅 시 로드 목록에는 계단·플레이어만 있었다. 즉 **캐릭터를 사서 장착하고 앱을 닫으면
다시 열리지 않는다.** 무기가 안 보인 것도 같은 원인이다(`weapons` 도 lazy).

고친 방법: 저장본을 **에셋보다 먼저** 읽고, 고른 캐릭터·무기에 필요한 번들을 부팅 목록에
더한다. 첫 화면이 조금 늦어지지만 게임이 열리지 않는 것보다 낫다.

##### 2. 무기가 씬에 있는데 화면에 없었다 — 네 번 틀렸다

`attached: true`, `bone: handslotr`, 크기 1.17유닛(캐릭터 0.92보다 길다)인데 보이지 않았다.
칼날이 카메라 축과 나란해 몸에 가려진 것이었다. 세우려는 시도가 계속 어긋났고,
매번 **원인이 달랐다**:

| 시도 | 결과 | 원인 |
|---|---|---|
| 오일러 각 고정(−90° x) | 옆으로 누움 | 본의 월드 회전이 곱해져 상수로는 맞출 수 없다 |
| bbox 로 긴 축 자동 탐지 | 여전히 누움 | `Box3.setFromObject` 는 **월드** bbox 다 — 붙인 뒤 재면 본 회전이 섞인다 |
| 붙이기 전에 측정 | 여전히 누움 | `setFromObject` 가 **자손의 matrixWorld 를 갱신하지 않는다** — 갓 복제한 노드는 값이 낡았다 |
| 팩 규약(칼날 +y) 사용 | 여전히 누움 | **부착 시점에는 본의 월드 행렬이 확정되지 않는다** — 스킨드 본은 `mixer.update` 뒤에야 제 자리를 갖는다 |

마지막이 진짜 원인이었다. 정렬을 **첫 프레임 뒤로 미루자** 해결됐다
(`alignHeld` 를 update 루프에서 한 번 부른다).

이 과정을 데이터로 좁힐 수 있었던 것은 `__ie.weapon` 훅에 **홀더의 로컬 축이 월드에서
어디를 향하는지**를 실어 보냈기 때문이다 — "안 보인다" 만으로는 네 원인을 구별할 수 없다.

##### 3. 첫 화면 설명이 낡아 있었다

"맞히면 계단이 열린다"는 이제 사실이 아니다(계단은 항상 열려 있고 문제는 보스전에만 있다).
방향·가짜 계단·보스 관문으로 다시 썼다.

##### 확인한 것

| 항목 | 결과 |
|---|---|
| 난이도 칩 5개 | **한 줄에 들어간다**(세로 420px) — 지난 라운드의 미확인 항목 |
| 상점 목록 | 28종 · 무기 22 + 캐릭터 6 · **가격 오름차순** · 받은 가격 그대로 |
| 구매 | 골드 30,000 → 16,000 차감 정확 · 중복 구매 버튼 사라짐 · "가지고 있어요" 표시 |
| 무기 장착 | 로비 목록 "없음 + 산 무기", `handslotr` 본에 부착, **세워 든 자세** |
| 캐릭터 교체 | ⭐ 기사가 목록에 들어오고, 바꾸면 **`Idle_A` 재생**(T 포즈 아님) |
| 보스전 | 정답마다 **플레이어 `Throw` ↔ 보스 `Hit_A`**. 40층 보스(HP 96) 8문제로 처치 — 절반 적용 확인 |
| 계단 | Block Bits 3종이 섞여 보인다(초록·흙·자갈) |
| **가짜 계단** | 회색 격자(`prototype`)가 진짜 옆에 **한눈에 이질적으로** 보인다 |
| 성능 | 등반 55~65 call · 34~36k tri · **60fps** |

**보스전 draw call 63~65 로 예산 60 을 넘는다** — 스킨드 보스(11)와 계단 블록 3종이 겹치는
구간이다. 삼각형은 36k(예산 150k)로 여유가 있고 fps 는 유지된다. 실기기에서 다시 재야 한다.
